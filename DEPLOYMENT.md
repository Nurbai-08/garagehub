# Деплой на Vercel

Проект настроен как два Vercel Service на одном домене: Vite обслуживает интерфейс, FastAPI — `/api/*` и `/health`. Поэтому `VITE_API_URL` на Vercel задавать не нужно.

## Однократная настройка

1. Импортируйте корень репозитория в Vercel.
2. В `Settings → Build and Deployment` выберите Framework Preset `Services`.
3. В `Storage` создайте публичный Vercel Blob store и подключите его к проекту. Vercel добавит `BLOB_READ_WRITE_TOKEN`.
4. Подключите постоянную PostgreSQL и добавьте её строку соединения как `DATABASE_URL`. Предпочтителен pooled URL провайдера.
5. Добавьте `JWT_SECRET` длиной не меньше 32 случайных символов.
6. Добавьте `ENVIRONMENT=production` для Production environment.

Для Preview и Production нужны отдельные постоянные базы либо осознанно одна общая база. Blob token и `JWT_SECRET` должны быть доступны в каждом окружении, которое вы собираетесь деплоить.

На каждом build backend запускает `alembic upgrade head`. Если обязательная production-конфигурация отсутствует, сборка завершается ошибкой до публикации — приложение не переключится обратно на временный локальный диск.

## Демонстрационные данные

После первой миграции можно один раз выполнить seed с доступом к production-базе:

```bash
cd backend
python -m app.seed
```

Команда создаёт demo-пользователей и BMW G30. Его изображение входит в статические assets frontend и не зависит от диска backend. Все новые изображения, загруженные через форму, сохраняются в Vercel Blob.

## Проверка после деплоя

- `https://ваш-домен/health` возвращает `{"status":"ok"}`;
- BMW отображается в каталоге;
- загрузите тестовое фото, затем выполните redeploy: оно должно остаться доступным по URL Vercel Blob;
- `https://ваш-домен/garage` открывается напрямую без 404.
